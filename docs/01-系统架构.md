# 系统架构

第一版采用四段流水线：加载文档 → 分块建索引 → 混合检索 → 按路由生成。

## 设计选择

| 设计 | 做法 | 原因 |
|---|---|---|
| 流水线 | 四模块拆开 | 评测时能单独看是检索失败还是生成幻觉 |
| 检索 | 向量（BGE）+ BM25，RRF 融合 | 游戏名、标签适合关键词；氛围/手感适合语义 |
| 文档形态 | 一款游戏一个 Markdown 父文档，按二级标题切子块 | 小块检索更准，生成时回整份档案保证上下文 |
| 元数据 | app_id、价格、语言、平台、好评率等做过滤 | 「100 块以内、要中文」不该只靠向量 |
| 路由 | recommend / detail / library / trending | 贴合玩家问法；热门与档案问答不能混用一条路 |
| 图谱 | 第一版不上 | 没有评测证明关系检索是当前瓶颈 |

## 模块

| 文件 | 职责 |
|---|---|
| `src/config.py` | 路径、模型、top_k |
| `src/rag_modules/data_preparation.py` | 加载 Markdown、解析字段、父子块 |
| `src/rag_modules/index_construction.py` | 嵌入与 FAISS |
| `src/rag_modules/retrieval_optimization.py` | 混合检索与元数据过滤 |
| `src/rag_modules/generation_integration.py` | 路由、查询重写、带引用约束的生成 |
| `src/main.py` | 交互入口、库存约束、简易规则过滤 |

## 落地顺序

1. 用固定问题集定义「答对」长什么样
2. 入库 50–200 款游戏档案
3. 校准切分与过滤
4. Prompt 只依据档案回答
5. 回归评测后再加能力
