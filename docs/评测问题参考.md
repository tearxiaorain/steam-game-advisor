# 评测问题参考

来源：本文件由一份 LLM 草稿改写。原稿覆盖面全，适合当**题库**；不能直接当第一版 Benchmark。很多问法依赖剧情、补丁、实时榜单，商店语料里没有，拿来打分只会逼模型幻觉。

用法：

- **第一版评测集**：只跑「范围内」的题目，每题要有预期行为，不只看文笔好不好。
- **题库/以后**：范围内=否的题目留着，接了评论、补丁或 API 再启用。
- 打分至少看三件事：路由是否走对、该召回的 `app_id` 在不在 top-k、没有依据时会不会拒答。

难度：Easy = 单实体或单字段；Medium = 多项元数据；Hard = 语义相似、不好靠标签精确命中。

## 3. 怎么打分（第一版够用）

每题记 4 个位，不要只看「答得像不像人」：

1. **路由**：recommend / detail / library / trending 是否走对。闲聊应被改写，热门不得进向量检索冒充榜单。
2. **检索**：需要具体游戏时，目标 `app_id` 是否出现在检索结果里（比较题要两款都在）。
3. **忠实**：回答中的价格、语言、平台、好评率、App ID 必须能在父文档或元数据里找到；找不到必须说没有。
4. **范围**：X01–X03 这类题，拒答或声明缺数据得满分；编造剧情/公式/补丁记严重失误。

建议第一轮人工跑 15–20 题（表 1 里语料实际覆盖到的），记下失败类型：切分、过滤、向量、还是 Prompt。再决定要不要加重排序或扩字段。

## 4. 和字段文档的对应

- 条件题（R05、R06、S03、S04）打不过：先查 `docs/字段与问题分类参考.md` 里元数据是否采到，再查过滤有没有接上。
- 相似题（R03、R04）打不过：先看简介/标签子块，而不是加 Graph RAG。
- 热门题（T01）答成「库里好评最高」：路由错误，不是生成问题。
