# 字段与问题分类

来源：本文件由一份 LLM 草稿改写。原稿把字段和意图想全了，有参考价值；下面冻成**第一版能采集、能过滤、能评测**的规格。更大的清单留在文末，不进入当前实现。

## 1. 字段：先分「进向量」还是「做过滤」

不要把所有字段拼成一个 `combined_text` 再整篇向量化。采用：**一款游戏一个父文档，按小节切子块检索，生成时回父文档**。

### 1.1 第一版必采（没有这些就不建库）

| 字段 | 类型 | 用途 | 进向量 / 元数据 |
|---|---|---|---|
| `app_id` | string | 唯一键、引用、库存对齐 | 元数据 |
| `name` | string | 展示、精确查找、BM25 | 两者都要 |
| `short_description` | string | 语义检索、一句话介绍 | 向量（简介子块） |
| `detailed_description` | string | 玩法/氛围详解 | 向量（玩法子块） |
| `genres` | list | 类型过滤与检索 | 两者都要 |
| `tags` | list | 风格/手感（类魂、像素、建造） | 两者都要 |
| `categories` | list | 单人、合作、手柄、Steam 成就等 | 元数据为主，可写入子块 |
| `developers` / `publishers` | list | 「V 社自己的」「同制作组」 | 元数据 + BM25 |
| `release_date` | date | 新作/某年发行 | 元数据 |
| `platforms` | list | Win / Mac / Linux | 元数据 |
| `supported_languages` | list | 是否中文（界面/字幕尽量分开记） | 元数据 |
| `is_free` | bool | 免费过滤 | 元数据 |
| `price_cny` | float | 「100 块以内」 | 元数据（带快照时间） |
| `review_desc` | string | 好评如潮 / 多半好评 等 | 元数据 |
| `review_percentage` | float | 好评率过滤 | 元数据 |
| `review_count` | int | 评测太少要降权或标明样本小 | 元数据 |
| `pc_requirements_min` | string | 最低配置类问题 | 向量（配置子块） |
| `fetched_at` | datetime | 价格、评测、折扣的时效 | 元数据，不进向量 |

父文档建议写成固定 Markdown，便于标题切分，例如：

```markdown
# {name}（app_id={app_id}）

## 简介
...

## 类型与标签
...

## 游玩方式
单人/合作/是否手柄...

## 配置与平台
...

## 语言
...

## 评价摘要
好评率、评测数、商店短评（若有）
```

### 1.2 第一版可缺，有则加分

| 字段 | 说明 |
|---|---|
| `name_cn` | 中文名，对「鹅捣乱」「带数字 2 的 V 社射击」这类查找很有用 |
| `about_the_game` | 若与 `detailed_description` 重复则只留一份 |
| `mac_support` / `steam_deck` | 比泛 `platforms` 更好过滤 |
| `positive_review_excerpt` / `negative_review_excerpt` | 各 1–3 条，支撑口碑类，**不要**把全量评论当第一版语料 |
| `content_warnings` | 恐怖、暴力等，服务「不要太恐怖」 |

### 1.3 明确后置（不是第一版知识库字段）

这些要么会过期，要么商店页根本没有，写进档案只会让模型编造：

- 当前在线、本周销量榜、史低价、TGA 提名热度 → 结构化 API / 另表，带时间戳
- DLC 清单、截图、官网链接 → 展示用，不驱动第一版检索
- `peak_ccu`、`estimated_owners` → 可选统计，不当前置过滤条件
- 剧情设定、战斗公式、版本更新说明 → 攻略语料，第一版不收录；问到了应拒答或声明库中没有

### 1.4 不要做的两件事

1. **不要**把简介+标签+价格+评测拼成单一向量，再放弃子块。价格和中文支持用元数据过滤，氛围和「像某款游戏」用语义子块。
2. **不要**把会变的价格、折扣、在线人数写进长期向量正文而不打 `fetched_at`。热门类问题走另一条路，见问题分类。

## 2. 问题分类：想细可以，路由先粗

原稿 7 类适合当**评测标签**，不适合第一版做 7 路分类器。系统先路由再检索。第一版只做 4 路处理逻辑，7 类问法映射上去即可。

| 第一版路由 | 对应原稿类别 | 系统怎么做 |
|---|---|---|
| `recommend` | 推荐、部分检索（条件筛选）、比较、部分闲聊 | 解析约束 → 元数据过滤 + 混合检索 → 返回 3–5 款并解释 |
| `detail` | 详解、精确查找、口碑（若有评测摘录） | 定位到 1 款（或比较时 2 款）→ 用父文档生成，强制引用 |
| `library` | 原稿缺失，但是 P0 | 用已导入库存当过滤/重排，再走 recommend 或「今晚玩哪个」 |
| `trending` | 热门/趋势 | **不走向量库**；无 API 时明确说没有实时榜，禁止用过期简介冒充「本周第一」 |
| （生成兜底） | 综合闲聊 | 先改写成 recommend/library，不单独做闲聊模型 |

比较类：第一版当作 `recommend` 或 `detail` 的多实体检索（两款都召回再对比），不必单开路由。

口碑类：有评测摘录就走 `detail`；只有一个好评率数字，就只能答商店统计，不能编「玩家都说优化差」。

闲聊类：能抽到约束（碎片时间、想吃东西）就改写成 recommend；纯情绪句给短回复并引导成可检索的问题。

## 3. 和产品范围的对齐

| 能力 | 字段/路由是否支撑 |
|---|---|
| 自然语言多约束搜索 | `tags`+`categories`+价格/语言/平台 + `recommend` |
| 可解释相似款 | 简介/标签子块 + 引用父文档 |
| 库存里今晚玩哪个 | `library` 路由；库存 `app_id` 与语料对齐 |
| 热门榜 | `trending`，第一版可声明未接 API |
| 攻略、机制、补丁 | 不采字段；评测里标为应拒答 |

## 4. 下一步

1. 用第 1.1 节当采集清单，先做 50–200 款，不追求全 Steam。
2. 评测问法以 `docs/评测问题参考.md` 里**第一版范围内**的题目为准。
3. 代码上仍是一个 LLM 路由（4 类），不要先上独立意图分类模型。
